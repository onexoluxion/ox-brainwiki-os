# OX Project Cabinet

Use this skill when a project needs a reliable entry point, task-specific source routing, a cleanup review, or a fresh-session retrieval check. It standardizes navigation and evidence handling; it does not replace the project's domain rules, authorize financial or operational actions, or make every project share the same folder names.

## Open a project safely

1. Start from the user-connected project folder and read its project index and task/source guide when present.
2. Select the named package or skill release before reading its references. Record its name, version and source. A newer timestamp, `UPDATED` suffix, account package, local mirror or successful-looking answer does not prove authority or installation parity.
3. Read only the route needed for the current task. For each route, identify:
   - the authoritative working file or system;
   - the evidence required and its coverage/as-of date;
   - the permitted destination for a result or handoff;
   - what remains unverified.
4. Use the supported resource reader for bundled references. Do not search protected configuration folders, bypass a permission boundary, or substitute an older package. Distinguish a missing source from an inaccessible source and stop only the affected action when a required reference cannot be read completely.

## Filing flow

Use this sequence for every project task:

`request -> entry map -> selected source route -> dated evidence -> authorized work -> validation -> saved result and handoff`

Keep the project's existing authoritative files and evidence locations. Do not create duplicate business records, nested knowledge bases or a generic folder template merely to make the cabinet look uniform. A project may add a small index or task guide when it improves routing and preserves the existing records.

## Build or repair the cabinet

For an authorized cabinet change, inspect the existing entry map, project instructions, active automation inputs and a small set of representative business tasks. Resolve source-location conflicts from dated evidence before writing a definitive route; when unresolved, label the affected route as blocked instead of choosing by timestamp.

Prefer updating an existing entry point. If absent, use the project's naming convention for one starting index and one compact task/source guide; in OX the established pattern is `PROJECT_INDEX.md` plus `kb/YYYY-MM-DD-task-and-source-guide.md`; the shipped `cabinet/templates/` follow it. Add topic pages only when the task routes genuinely need them. Do not create empty folder hierarchies.

Keep the index to purpose, current authoritative locations, selected package identity, result destinations and known gaps. Each task-guide row has: task or trigger, reference to read, authoritative working source, required evidence, and result destination. Keep business rules in their maintained source instead of restating them in the index. Distinguish package-relative resources from project-relative files and optional external vault references.

Prepare changes separately, check link targets and authority, preserve original bytes, and verify target files have not changed since review before applying the authorized navigation-only update. Compare the untouched scoped records afterward. Report exactly what the preservation check covered; a partial inventory is not whole-project proof.

## Preservation and cleanup

Preserve originals, backups, historical snapshots and distinct evidence. Similar names, old dates, repeated bytes or a newer-looking filename do not prove redundancy. Before any consolidation, moving, renaming or deletion, produce an explicit candidate list, check callers and references, identify the authoritative copy, and retain a recoverable record. Cleanup is a separately reviewed action; navigation pointers may be corrected without touching the underlying records.

## Fresh-session acceptance

Test the cabinet in a clean session before relying on it:

- ask representative tasks without supplying the answer;
- record the files actually opened, source routes chosen, evidence dates, failed lookups and effort;
- verify that competing package versions, stale source notes, duplicate-looking records and inaccessible references are reported rather than silently substituted;
- make no edits, connector calls or operational changes during the acceptance test.

Compare the new cabinet with the prior route using the same task set. Report measured retrieval changes; do not claim faster access without comparable evidence. A reported account-package result is not proof of byte identity, native installation, or cross-app parity.

## Completion report

Report the selected project and package, routes and sources actually read, authority and evidence dates, files changed, validation performed, unresolved gaps, inaccessible references and unsynchronized surfaces. State clearly whether the result is read-only, prepared, applied or only proposed. Save a dated handoff only where the project rules authorize it. Never claim completion when a required check was unavailable.
